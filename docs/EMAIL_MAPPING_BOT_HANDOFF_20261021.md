# TAP 邮箱映射到 Bot 单条定向通知：部署与验收

## 本轮交付范围与状态

基于用户上传的最新 `10.21 1704.zip` 修改，保留该版本的 Quota 修复、当前 App、风神取数与现有绝对值风险判断逻辑。权威人员表为：
https://bytedance.my.larkoffice.com/sheets/J4H8swHMIh0le6tcJbjmNzWnytp

本轮完成代码链路：
预警事件的 question_user_name → Sheet 中已确认且启用的精确姓名/风神姓名 → 企业邮箱 → 当前 Bot 应用的 open_id → 测试白名单强制覆盖 → 单条风险卡片 → 对应 Alert 工作台链接 → 真实发送结果台账。

**当前交付是源码更新包，不是可跳过构建的安装包。真实 Sheet 读取、真实飞书发送和真实链接打开均待 AIME 环境验收。未获取真实 Bot Token、未向飞书发送消息。**

本轮为阶段一：只验收当前绝对值事件的一条通知。今天会议的新阈值、上周窗口、简化 RCA/关闭流程、Revenue/Adv 明细、定时批次等留待阶段二统一更新；全量人员表完善和正式分发留待阶段三。阶段一测试成功不等于会议新规则已上线。

仅开放 test 模式下的显式单条发送。formal 模式只保留预览与失败关闭保护，没有开放正式发送入口。后台定时扫描、极端值自动发、观察名单审核后自动发不在本轮启用范围。不要把 auto_send_enabled 改为 true 当成上线方法。

## 一、AIME 先执行部署

1. 在当前同一个 App 实例替换源码，保留 `AIME_PLUGIN_DATA_DIR`、已有 `secrets.json`、`tap_casework.db`、`casework_notification.json` 和平台环境配置。不要把本包覆盖到持久化数据目录。
2. 先备份台账。运行时会新增确认票据表和通知审计字段，不删除已有事件。旧的未发送通知缺少凭证指纹/映射快照时会被阻止，需要重新预览和确认。
3. 执行完整 AIME 构建。包中不包含旧 `.aime_build/bin/server`、`app/server-go/bin/server`、`app/dist` 或 CDN 构建记录，避免新代码搭配旧二进制/旧页面。
4. 若在原工程原位更新，注意启动脚本优先执行 `.aime_build/bin/server`。必须重新生成实际启动的二进制；不能仅覆盖 release 的 `app/server-go/bin/server` 后保留旧 dev 二进制。正式安装使用平台标准构建/打包流程。
5. 重新启动并确认前端出现“确认发送单条测试卡片”。所有 Secret 只通过既有安全配置入口保存，不放在对话、代码包或测试报告中。

建议在 AIME 的原始私有依赖环境运行：
```bash
go test ./...
go vet ./...
python3 tools/gen_api.py . --check
```
前端在 `app/frontend` 目录执行：
```bash
pnpm run typecheck
pnpm run test:run
pnpm run build:local
```
本地独立工作台检查另见 `tsconfig.workbench.json` 和 `vitest.workbench.config.ts`。原生完整构建依赖 @aeolus/data-sdk、@aime-plugin/browser-sdk 等内部包；不能用空 SDK 或模拟模块替代后宣称生产构建通过。

## 二、确认人员表可以被当前 Bot 应用读取

当前配置保留原包中的 Sheet ID `e1e5ac`。先用当前 Bot 的应用身份检查工作表元信息，确认确有该工作表。若不一致，应由 AIME 依据真实返回确认后修改，不能猜测选择其他页。

表格前七列需要按以下顺序保留：

| 列 | 表头 | 用途 |
|---|---|---|
| A | 区域 | 同名多邮箱时辅助精确区分；不同区域名称不做模糊猜测 |
| B | 业务表原始姓名 | 与原提报人精确匹配，可中文或英文 |
| C | 已确认企业邮箱 | 必须完整且经人工核实 |
| D | 风神姓名 | B 与实际 question_user_name 不同的时候，填写实际原始值 |
| E | 匹配状态 | 仅“已确认”可进入发送链路 |
| F | 匹配依据/备注 | 人工核验说明 |
| G | 最近验证时间 | 维护追溯信息 |

姓名只进行首尾空格清理及大小写统一，不生成拼音、不猜测邮箱前缀、不模糊匹配。找不到、未确认、停用、多个不同邮箱且区域无法唯一确定时，必须阻止发送。

AIME 对话能读取此表，不代表当前 Bot 的 tenant_access_token 能读取此表。若后端失败，应按具体 API 错误检查文档授权、应用可用范围、对应接口权限和账号状态。必要时将该文档按企业允许的方式授权给当前应用。不要改用个人 Token 冒充用户，也不静默回退旧 CSV。

人员表按真实 grid row_count 分批读取，读取过程中 revision 改变则整轮失败，不使用拼接后的混合版本。数据及同步时间落共享 SQLite；预览和发送前仍重新拉取权威表。后续新增超过第 105 行也会被读取。

## 三、配置一个测试人员

1. 进入“预警处置收件箱 → 管理设置 · 通知集成 → 飞书 Bot”。
2. 保留已配置凭证，在测试白名单区域填一个已确认的完整企业邮箱。
3. 后端使用当前 Bot 查询 open_id，保存后通知模式为 test。白名单可以保留多个已批准测试人，但每次选择且发送一个；不接受 chat_id。
4. 刷新工作台重新加载配置和白名单。确保 `auto_send_enabled=false`，不要开启正式通知。

## 四、选择事件并生成预览

1. 从已完成的真实 ET 风险扫描打开一条事件，或打开已有且来源已核实的历史事件；历史指标要保留真实日期，不能说成今天的数据。
2. 确认 Account ID、原提报人、Region、CCR/NFS、指标窗口、触发原因和 Alert ID。
3. 用该事件负责人或治理运营账号打开“责任分派与通知”。选择指定测试人员，点击“生成无发送预览”。
4. 预览必须显示：精确匹配成功、脱敏邮箱、当前 Bot 解析成功、实际目标是测试白名单用户、test 模式、will_send=false。未完全通过时确认框和发送按钮不可用。
5. 若原提报人在 Sheet 中未确认/未匹配，即使测试收件人存在，也应阻止本次链路验收；不能绕过原姓名到邮箱这一步。

确认票据有效期 10 分钟，绑定操作者、事件版本、指定测试目标、映射版本和 Bot 凭证指纹。Secret 不写入票据、日志或前端。票据只以随机值返回，数据库保存其哈希。

## 五、明确确认后发送一条

1. 用户核对预览后勾选确认框，点击“确认发送单条测试卡片”。
2. HTTP 202 和“已入队”只表示请求已保存。后台 worker 继续刷新人员表、检查映射未变化、重新解析当前 Bot 的 open_id，并强制覆盖为被选中的测试人。
3. 只有飞书返回成功且非空 `message_id`，通知记录才标记 sent。页面会展示原始 message_id；人员 ID 和邮箱仍脱敏。
4. 要求测试人员实际确认收到 TEST 卡片，并点击进入同一个 Alert。收到消息不等于已读、已处理。
5. 不需要卡片动作回调。本轮在工作台处理，因此公网 callback/challenge 不作为这条通知链路的前置要求。

发送错误或超时立即停止，不自动退避重发；blocked 也不会等几分钟后突然发送。修复后重新预览、确认，才可人工重试同一通知。消息使用稳定 uuid，但平台去重有时间边界；超时或进程中断属于投递结果不确定，先核对收件端/消息记录，再决定是否重试，不能承诺跨任意长时间绝对不重复。

## 六、必须返回的真实验收记录

| 项目 | 需要的证据 |
|---|---|
| 来源 | Alert ID、客户 ID、原提报人、指标窗口、指标与规则 |
| 映射 | Sheet revision、行号、记录版本、匹配别名、脱敏邮箱 |
| 解析 | Bot 的脱敏 App ID、解析结果、脱敏 open_id |
| 实际接收人 | 指定测试人、test 模式、实际目标脱敏 ID、测试替换标识 |
| 发送 | 最终状态、尝试次数、真实 message_id、错误码和可公开错误原因 |
| 页面 | 测试人实际收到消息，点击后打开的 Alert ID 与原事件一致 |
| 幂等 | 重复点击不重复生成发送任务；失败后不会自动发第二次 |
| 持久化 | 刷新及正常服务重启后，事件和通知记录仍可查询 |

不得在验收报告中包含 Secret、Access Token、JWT、确认票据或完整人员 ID。正常业务信息本轮只发指定测试账号，不扩散业务群和其他提报人。
