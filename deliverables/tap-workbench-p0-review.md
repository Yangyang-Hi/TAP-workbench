# P0 审计与规则说明

## 1. 结论与规则

现有规则适合发现风险、供人工复核；它不能证明违规或治理效果。Top20 是相对排序，即使整体风险很低仍可能产生观察名单，不能直接当作极端风险。Current QTD 与锚点前后比较是两组时间窗口，页面需明确区分。

已落实用户确认：

- 绝对值观察：P0 CCR≥3 且 P0 NFS>50。
- 绝对值极端：P0 CCR≥45 且 P0 NFS≥300。
- 增幅观察：每个 Program×Tier×Region 的有效正增幅客户 Top20；负增长、零增长、无有效增幅不参与。客户去重排名，不以分页或筛选后重新排名；同一客户的不同保护事件仍保留。
- 增幅极端：增幅>100% 且 Current P0 CCR>6。
- 相对增幅=(Post CCR−Pre CCR)/Pre CCR×100%；必须有有效非零基线和完整窗口，不平均源 CCR。
- 两类同时命中独立成组：仅增幅＋仅绝对值＋同时命中=全部预警去重客户；保留原始命中标签。极端优先于观察。
- ET 继续使用已经验证的 create_time 锚点；THT 用实际保护开始日；ST 用实际名单开始日。ET/THT 锚点前7天与后7天；ST 前3个日历月与后3个日历月。边界为前闭后开：Pre=[anchor−周期,anchor)，Post=[anchor,anchor+周期)。不是猜季度首尾。
- 正式扫描的绝对值 Current 为批次截止日所在季度起点至该截止日，明确保存 current_window；扫描周/事件ID仍沿用原窗口，防止深链失效。
- 比较窗口尚未完整、缺锚点、源 NULL、零基线时，该比较不可评估；有其他有效独立规则命中仍可预警。所有规则均无命中则不进入风险列表；诊断和正常客户仍保存在扫描事实中。
- 内部仍使用既有 extreme/watch/normal 状态；extreme 对应用户 critical 业务含义，不重命名既有枚举和事件协议。

Cloud 中已配置的生效规则仍是权威。本次不越权覆盖 Cloud 配置；AIME 必须核对有效规则与上文一致，若有差异通过原管理与版本控制流程调整。安装代码不会自动把旧批次按新规则重写。

## 2. 查到的问题与修复

1. 原先对全客户先做 ADV/Revenue 等 enrichment，随后才完成比较与风险判断。现改为加载目标与锚点→核心 Current→Pre/Post与增长→阈值/Top20→保存首版风险→仅对风险客户补明细。可选明细失败不改变已确认的核心事实。
2. 原 ST 不完整或无明确时间合同的数据不能证明 QoQ；现只接受实际锚点、完整3个月窗口及有效源值。缺少开始日期不再猜造固定日期。
3. 原分类可重叠，分页/二次筛选可能影响排名。现完整已保存批次先判断与排名，之后筛选及分页；三分类互斥，按客户计数。
4. 原卡片概念混合通知、客户与事件。新增 risk_customers / pending_customers / in_progress_customers / closed_customers；后三项互斥且加和等于当前风险客户数。旧 pending/handled/closed 字段保留原语义，通知成功不当成治理完成；列表另显示预警记录数。
5. 原历史模式没有正确加载保存模型、旧代码按每人最多10批清理。现历史请求正确读取已保存周度；移除该清理，并增加独立 tap_scan_history.db SQLite事务归档及缺失JSON时恢复。旧规则已经删除的历史不能凭空恢复。
6. 风险筛选移除 normal，自实际风险池取 Region、提报人和状态；搜索包括 enrichment 中的 Advertiser ID及名称，避免只搜主ADV。Case 状态不能串到不同提报/保护事件。缺行/失败明确显示，不能作0个风险。
7. 补数/回填继承已保存 Current 时间口径；混合旧周度与新 QTD 不能静默合并。无法证明窗口的历史事实保持限制，需新扫描核验。
8. 原 Quota 候选与正式 Cloud 事件/通知读取存在缺口。现 ET/ST 分别识别超额，通过现有 Cloud Case 和通知路径处理；接收人为对应 Region 的正式 Regional POC，并在预览及发送前重新验证映射。组合区域有不同POC时阻断，不任意选一个。候选/排队不显示已发送，正式回执才是成功；失败无法读状态时显示未知。

## 3. Quota 边界

- 复用当前配额聚合、去重与源过滤；不发明新的配额分母。
- 沿用现有阈值：ET≥100%，ST严格>100%，数据完整且有正式分母；THT无分母不报警。
- Regional POC 与风险客户的真实提报人是不同收件人来源；下游仍复用原 Preview Token→人工确认→Outbox→发送前复核→通知记录。
- 安装、打开或刷新页面不会自动正式发送。未更改自动发送开关。旧的 pending/candidate 不是发送成功证据。

## 4. 限制与验收边界

- 本地没有真实源/Cloud/飞书凭证，测试使用隔离存储与受控响应，不证明生产所有目标客户当前均有源值。
- 目标客户池沿用现有配置：ET/THT现有名单起点、ST现有季度名单，并非整个历史所有TAP客户。现有每Program最大6000预算保留；超量须明确失败/不完整，不能静默裁剪。大样本ET2150、THT5400分批覆盖测试通过。
- 对比窗口尚未成熟时不能提前补齐/造值，ST三个月Post窗口可能导致增长暂不可评估，但绝对值仍可判断。
- 当前修复不覆盖首屏数据总览指标合同、图表、导航和报告，不替换 API schema/typed client；响应只新增只读字段。现有 Cloud 事件、打标、状态机与通知原记录不重建。
- SQLite只是新增扫描历史归档，不替代Cloud权威事件和处置记录；必须持久化应用数据目录。生产需确认数据目录可写、重启保留、备份包含SQLite一致性要求。
